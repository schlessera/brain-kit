# Storage ownership and capacity accounting

Discovery for [#1780](https://github.com/schlessera/brain-kit/issues/1780),
informing [#1779](https://github.com/schlessera/brain-kit/issues/1779) and the
design in [#1782](https://github.com/schlessera/brain-kit/issues/1782).
Source reviewed at `f2c98da6093c9e1731f061625ba7302f51bf7340`.
This is a proposed model, with a fixture experiment, not a shipped collector,
retention decision or cleanup authorization. Existing stats and MCP meanings
remain unchanged. Cleanup/recovery policy is the separate #1781 discovery.

## Recommendation

Use one inventory of permitted storage objects, with separate **ownership
views**, **capacity scopes**, and **measurement evidence**. Brain and deployment
are views over that inventory, not two quantities to add. Keep filesystem
allocation estimates separate from logical file sizes and actual volume usage.
Start with local metadata and configured application stores; leave remote
storage, quotas and host runtime stores unknown unless explicitly observable.

Core owns deterministic content/Git measurement through a later supported CLI
JSON operation. ui-server resolves its effective configuration, adds its stores,
merges duplicate identities and serves authenticated inventory. It must not
import core internals or put operational state into `brain.db`. Backends retain
their transcript layout and lifetime ownership. No storage-provider seam,
privileged host browser or worker-accessible inventory is proposed.

The binding constraints are [the roadmap](../../ROADMAP.md#what-binds-future-work),
[governed writable workers](../decisions/governed-writable-workers.md),
[worker writable areas](../decisions/worker-writable-areas.md),
[the recovery guide](../inbox-recovery.md), and the existing
[machine contract](../integration-contract.md). Navigation and presentation
remain for #1782 under [navigation](../decisions/design-kit/navigation.md) and
[sessions and drafts](../decisions/design-kit/sessions-and-drafts.md).

## Three identities and honest units

An **entry identity** represents a visible name within a permitted root. Use an
opaque stable root ID plus normalized relative path; rename/replacement needs a
new revision or explicit continuity evidence. Do not publish inode numbers or
absolute private paths as stable public IDs. An **object identity** deduplicates
the bytes: on tested Linux local filesystems, `(device, inode)` for the scan
epoch, validated again when reopening. Inode reuse, remounts and remote/overlay
filesystems limit cross-scan stability. A **capacity identity** represents one
allocation/quota pool in the process mount namespace, with provenance.

Canonical paths deduplicate nested roots and aliases, but are insufficient for
hard links or bind mounts. Use mount information plus device/filesystem evidence;
bind mounts of the same filesystem normally share capacity even when mount IDs
or root strings differ. Separate quota domains need separate quota identities.
Unknown equivalence must remain unknown, not cause guessed capacity addition.
An overlay's backing-store relation is not inferred from its device number.
Nested repositories/worktrees have their own ownership boundaries, and may share
a Git common directory or alternate object store: resolve those via
[Git path operations](https://git-scm.com/docs/git-rev-parse), never by assuming
`.git` is a directory. Do not follow alternates outside approved roots.

For regular files, logical bytes are `st_size`; on Linux allocated bytes are
`512 * st_blocks`, not `st_blksize * st_blocks`. Directory allocation and link
objects belong in a metadata bucket. Directory `st_size` is not user content.
Sparse files can have large logical size with tiny allocation. Compression,
reflinks, snapshots and shared extents prevent inode-based sums from proving
exclusive physical usage or reclaimable space. Report the allocation basis and
its limits. No content hash read or per-blob history analysis is necessary.
See [Linux stat fields](https://man7.org/linux/man-pages/man3/stat.3type.html).

For a supported filesystem observation, using its reported allocation unit `b`:

```text
total = blocks * b
used = (blocks - bfree) * b
free = bfree * b
available_to_caller = bavail * b
reserved_or_unavailable_free = free - available_to_caller (if meaningful)
```

`used + available` need not equal `total`. Keep quota used/limit/remaining as
separate nullable measurements; do not infer quotas from `bavail`, or substitute
a worker admission budget. Tmpfs has its own finite mount capacity and may
consume memory/swap; it is not extra persistent disk. Remote repository usage,
remote limits, and local Git bytes remain different scopes. A provider may
report repository logical storage rather than physical allocation; unsupported
remote measurement is unknown, without issuing a network request. Capacity
semantics follow [Linux statfs](https://man7.org/linux/man-pages/man2/statfs.2.html).

## Worked accounting

These numbers illustrate the model in MiB; they are not installation evidence.
Assume ordinary non-shared allocation for these examples.

One volume V: content 100, Git 40, index 10, scratch 5, staging 8, UI DB 12,
transcripts 20, journal 15, backups 30. The resolved object union totals 240.

```text
V capacity: total 1000; used 600; free 400; available 350; reserved free 50
app inventory allocated: 240
  brain ownership: content 100 + Git 40 + index 10 + scratch 5 = 155
  server ownership: staging 8 + DB 12 + transcripts 20 + journal 15 = 55
  operator backups: 30
volume used outside attributed inventory: 360 (only under these assumptions)
```

Staging is physically under the brain root. A whole-root physical view is
163, while server ownership is 55. Adding them with backups gives 248 and
duplicates staging. Likewise, including scratch in a deployment view and in
the brain view duplicates scratch. The inventory union is 240, and available
capacity is shown once as 350, not once per store. A 6 MiB file hard-linked into
scratch remains one object: its two entry rows show the alias relationship;
physical rollups allocate it to one primary bucket or a shared bucket, never
two parents. Content-path logical filter totals can still count both visible
names, explicitly labeled as file entries rather than unique objects.

Separate volumes: move brain/scratch/staging to V1, DB/transcripts/journal/backups
to V2, and turn temp to tmpfs T:

```text
V1: inventory 163; total 500; used 300; free 200; available 180
V2: inventory 77;  total 800; used 400; free 400; available 350
T:  inventory 4;   total 64;  used 4;   free/available 60
persistent attributed union = 163 + 77 = 240
```

An upload to V1 has 180 available, not `180 + 350 + 60`. A journal write to
V2 uses its 350; a turn additionally meets T's limit and the host ledger's
admission rules. A bind alias of V1 adds no capacity. A separately mounted Git
object store adds its own permitted store/capacity row, not imaginary space
under V1. Shared extents or uncertain mount equivalence make sums estimated;
do not show a negative residual or call it exact host-wide attribution.

## Inventory needed by the treemap and file workflow

Proposed fields, to review before naming any CLI command or HTTP route:

| Field group | Meaning |
| --- | --- |
| Identity | Inventory/scan ID, stable root ID, opaque entry ID, parent ID, revision, scan-local object ID, aliases/shared-accounting bucket, capacity ID or unknown |
| Ownership | Core/server/backend/operator owner, category, persistence/authority, permitted operation capability supplied by owner; no deletion inferred from category |
| Hierarchy | Permitted relative path, display name, parent/children or paginated continuation, explicit nested-store boundary; ancestors hold aggregates, not additional bytes |
| Classification | Regular/directory/link/special; normalized extension and its provenance; MIME only if already recorded; tracking facet tracked/untracked/ignored/unknown; indexing facet indexed/excluded/unindexed/unknown with reason |
| Values | Decimal integer byte strings for safe JSON precision; logical bytes, allocated bytes nullable; entry count and unique object count; subtree totals with a declared metric/basis; no mixture of compressed/uncompressed or logical/allocated values |
| Evidence | Method/source, exact/estimated/unknown accuracy, complete/partial coverage, observation start/end, owner revision where available, observed-at, cached-at, stale-after, errors/reasons and omitted entry count when knowable |
| Capacity | Total/used/free/available, quota identity/values nullable, tmpfs limits, remote scope/provider capability if observable; units and identity confidence |

Use logical **regular-file entry** size for `PDF > 5 MB`: MB means 1,000,000
bytes, comparison is strictly `> 5,000,000`, and MiB is a separate choice
(`> 5,242,880`). Case-insensitive extension classification is explicitly
filename-based, not verified MIME. Do not read attachment contents for size or
type sniffing. Exact-boundary files fail the strict filter. Show matching entry
count and logical total, plus unique objects/allocated estimate when known;
symlinks are link rows, not PDF targets. Filtering partial inventory shows a
known subtotal with a visible incomplete warning, not a complete result count.

Ignored/unindexed PDFs appear in this inventory without changing indexing
policy. Existing indexed IDs/types/references may enrich results, with their
index freshness; absent references are unknown, not proof of no incoming links.
No comparison between stale metadata and a current file authorizes cleanup.
The treemap switches a single size basis at a time and represents unknown/
unattributed storage outside proportional known tiles. It must not render an
unknown zero-sized tile as though nothing occupies space. #1782 owns visual
design; #1781 owns inspection/consequence/operation rules.

## Bounded read-only collection

Resolve an allowlist from existing owner configuration. Never accept a request
path as a scan root. Do not scan home, `/tmp`, runtime-host storage, credentials
or unknown mounts to fill a gap. Explicitly approved root aliases are resolved
once; descendants use descriptor-relative no-follow directory traversal and
inode/device checks before reading metadata. No FIFO/device opens, symlink
target traversal, implicit automount exploration or filesystem-crossing recursion.
Same-device bind mounts need mount-boundary checks as well as device checks.
An approved nested mounted store gets a separate root and is merged by identity.

Production proposal: one scan per app, two metadata workers maximum, 100,000
visited/queued entries, 30 seconds elapsed, bounded page/error buffers, maximum
depth 64, and cancellation at directory iteration and before each I/O/process
operation. Budgets are candidate defaults to qualify, not established runtime
promises. Kill/reap any bounded Git subprocess on timeout/cancel; a blocking
filesystem call may need a separately cancellable child process, because an
AbortSignal alone cannot interrupt kernel I/O. Git observations disable optional
locks, run with controlled config/environment/hooks authority, and never invoke
maintenance. No writes, checkpointing, index rebuild, packing or creation of
missing store directories happen during measurement.

Writes continue during observation. Validate metadata when opening directories
and before emitting inspected files; detect disappearance/replacement and record
changing evidence, not a snapshot guarantee. A coherent point-in-time DB byte
inventory is not obtained by copying the live main file; opening a new writable
SQLite handle could create sidecars. Read filesystem metadata only, and use
existing owner counters if read-only. Cache successful/partial scans with scan
IDs and a proposed 60-second freshness window; bound cache entries/bytes and
coalesce refresh requests. Low-space checks can refresh capacity alone.

Accuracy and completeness are independent:

| Observation | Required report |
| --- | --- |
| Stable regular file on supported local FS | Exact observed logical bytes; filesystem-reported allocation, estimated exclusive physical attribution |
| Sparse/compressed/reflink file | Logical exact at observation; reported allocation with basis; reclaimable space unknown |
| EACCES directory | Partial parent subtree, known bytes lower bound, inaccessible child count unknown; no zero-size claim |
| File changed/disappeared during scan | Partial/changing with interval/reason; bounded retry optional, no silent omission |
| Time/entry/depth/cancellation limit | Partial with continuation only if safely resumable; never call cached subtotal complete |
| Capacity permission failure or unsupported identity | Unknown capacity/identity; preserve known store bytes without invented available space |
| Quota unavailable | Unknown quota; known `bavail` remains filesystem availability, not quota headroom |
| Packed Git | Exact observed pack/index file sizes, coarse Git KiB report, unknown exact per-file/history attribution |
| Remote provider unimplemented/unavailable | Unknown remote usage/limit, no local substitute or default zero |
| Root absent vs unreadable | Absent may be exact empty only after successful parent resolution; permission errors remain unknown |

## Growth and low-space evidence

The later [growth proposal](storage-growth.md) specifies candidate fields, bounds,
cadence, guidance and synthetic decisions without approving production policy.

Reuse concepts from core stats history (nullable values, date/version provenance,
UTC buckets and thinning), not its schema/file or core authority. That file stores
corpus/index figures and lacks capacity IDs, coverage/basis and server ownership;
blindly reusing it would change the existing stats contract. Recommend a server
owned aggregate history, initially capped at 128 samples / 256 KiB, recording
per-category and per-capacity values with scan IDs, interval, basis, partial
reasons and metric version. No per-file histories, private paths or complete
inventory snapshots in history. Its own bytes count in server storage.

Only comparable scopes/bases produce growth rates. Unknown or partial samples
break the rate rather than contribute zero; deleting/adding a root or changing
capacity identity also breaks comparability. Capacity-only observations and
reservations remain distinct. Refresh after an owner-reported completed mutation
and on explicit request, with coalescing; a rate-based exhaustion estimate is
estimated and unavailable with insufficient comparable evidence. Low-space
signals name the affected write target's capacity/quota, freshness and margin.
Alert thresholds, cadence and persistence require later design; this spike does
not authorize automatic cleanup or a new retention policy.

## Synthetic experiment and evidence

Run `python3 -B docs/plans/storage-accounting-experiment.py` as an unprivileged
Linux user. The script accepts no external roots and creates only temporary
Odysseus fixtures. Git initialization, commits, packing, linked worktree, separate
Git directory, hard links, permissions and attachment writes are **fixture
setup**, not collection. Measurements use metadata and bounded local subprocesses;
no provider/network, attachment reads or real deployment corpus is involved.

Observed with Python 3.15.0, Git 2.55.0, GNU du 9.11, Bun 1.4.2:

- 2,103 distinct entries including 2,000 small crew files: 23,309,497 logical
  bytes and 8,478,720 allocated bytes; baseline 18.919 ms, overlapping-root
  scan 19.155 ms. Both exactly matched independent `du -s --apparent-size -B1`
  and `du -s -B1`. Root/path-dependent Git fixture sizes and timings may vary.
- Initial naive inclusion of directory `st_size` overcounted apparent bytes by
  43,460. Excluding directory logical sizes restored agreement; directory
  allocation remains in the allocation total. This mismatch is why the model
  distinguishes directory metadata from content.
- The 6,000,000-byte sparse PDF occupied 4,096 allocated bytes. The strict
  decimal PDF filter returned three entries / 18,242,880 logical bytes,
  including ignored and uppercase-extension files, excluding exactly 5 MB.
  A hard-linked server alias did not duplicate union allocation/logical bytes.
- Seven loose Git objects became seven packed objects in one pack during setup.
  `count-objects -v` then reported `size-pack: 1` KiB (1,024 bytes), while
  pack plus index allocated 8,192 bytes; the pack file alone had 593 logical
  bytes. This deliberate mismatch disproves treating Git's coarse report as
  full allocated Git-directory usage. See [Git's report units](https://git-scm.com/docs/git-count-objects).
- Actual linked worktree resolution shared the main Git common directory;
  separate-git-dir produced a `.git` file. Shared/overlapping roots measured
  once. Symlink loops/external targets were not traversed. `/dev/shm` permitted
  a second real capacity identity, and its file was counted only when its
  temporary root was explicitly included. No mounts were created.
- `statvfs` total/used/available agreed with independent
  `df -B1 --output=size,used,avail` (all three deltas zero in this receipt).
  Live host writes can change used/available between calls; the experiment
  records deltas rather than demanding a stable whole-filesystem snapshot.
  A separately changed fixture file invalidated size/mtime/ctime continuity.
- Real mode-000 directory enumeration returned `PermissionError`, preserving
  partial semantics; entry/time limits and cancellation were visibly partial.
  Before/after descendant metadata (identity, size, blocks, mode, mtime, ctime,
  link count) agreed across the observation pass. Atime is intentionally not
  a read-only invariant. The separate permission probe changes only its own
  temporary fixture; root timestamps are excluded from that comparison.

Three restored mutations demonstrated live assertions: replacing inode identity
with path identity failed `allocated aggregate agrees with du`; changing `>`
to `>=` failed the strict PDF count/boundary assertion; ignoring cancellation
failed `cancellation is visible`. The restored script passed. These qualify the
fixture observations, not a shipped production guard.

The script is a single-process prototype: it does not qualify descriptor races,
mount/bind traversal, exclusive extent accounting, real quotas, compression,
remote providers, live DB coherence, hostile directory renames, process-kill
cancellation, long blocking I/O or production-scale performance. It uses
scan-epoch Linux device IDs as its capacity proxy; that is not the complete
production capacity resolver. Other platforms and a root execution require
separate qualification (root cannot demonstrate ordinary EACCES).

## Alternatives, open decisions and implementation boundaries

An index-only report is cheap but misses unindexed/ignored attachments and
server state. Summing `du` per store is simple but double-counts aliases and
capacity and cannot express authority. Host-wide/runtime API scanning offers
more coverage but exceeds ordinary app access and requires a separately approved
host contract. Detailed historical Git attribution is expensive, often inexact
with deltas/shared objects, and unnecessary for the first honest overview.

Recommend the local permitted-object model above. Remaining choices for later
review are metric defaults in the treemap, snapshot/refresh/alert cadence,
history byte/sample caps, large-corpus pagination and resumability, platform
support and allocation terminology, capacity identity on overlays/quotas, and
whether remote-provider or runtime-host metrics are worth a separate scope.
These do not block this discovery deliverable; they must not be silently decided
by a future implementation.

Proposed implementation slices, not commitments or status:

1. Core local content/Git metadata inventory and bounded traversal, preserving
   stats; additive CLI JSON contract plus fixture/mutation proof for aliases,
   budgets, unknowns and Git path resolution.
2. ui-server owner-root registration and backend-owned transcript resolution,
   object/capacity merge and authenticated cached transport. No new public SDK
   seam; inventory access needs host/operator authorization reviewed separately
   from ordinary content read permission. Public health remains minimal
   (`createStatusRoutes`, `packages/ui-server/src/routes/health.ts:57-77`).
3. Server-owned bounded aggregate history/capacity refresh and low-space signals,
   after cadence/threshold design; no persistence in core `brain.db`.
4. The #1782 treemap/list/filter/inspection design, followed by separately scoped
   implementation with real browser/accessibility proof. Cleanup uses #1781's
   reviewed owner operations and independent confirmation/recovery rules.

Each new supported command/JSON/HTTP/config surface requires same-commit contract
documentation, appropriate `CONTRACT:` changes and consumer changesets when it
ships; none is introduced here. Names and schemas are intentionally unselected.

No concrete generated-host change is established: current configured stores and
ordinary `stat`/Git access are enough for this first model. The existing hosting
template #9 already owns backup scheduling/storage policy. If later discovery
requires mounted metric files, declared host capacity identity or a runtime
collector, file a bounded `brain-hosting-template` counterpart then; no Docker
socket or privileged inventory is implied by this document.
